Spaces：多人空间、Agent 互通与 Tanka 接入

对 Orca、Mirasim 和 Tanka/Ridge 接入面做了一轮调研，加上 very-happy 代码现状盘点，整理成一份高层设计和分阶段清单。本页只讲概念、取舍与顺序，不进实现细节。

  1. very-happy 今天的一切都挂在单个账号下。没有组织、成员、权限；Agent Teams 是同账号同机器的编排；agent 不是实体，只是会话上的一个字段；Tanka 接入是仓库外的私有适配器，全部以 owner 身份执行。
  2. Orca 和 Mirasim 各强一半。Orca 强在「编排契约给 agent 用」和「状态机三处投影」，但没有账号与团队。Mirasim 强在「空间即服务端」、群聊 @助手、会话互联协议、事项枢纽，但桌面优先、数据留在自己云、没有 Tanka。
  3. 「数据在 Tanka 体系内」的可达上限是三件事：Tanka 身份、Tanka AI 经 Ridge 查到 very-happy 数据、事件进 Tanka 群。开放平台没有自定义 agent 注册、没有普通消息事件、建群拉人受限，所以空间状态和 agent 间消息只能留在 very-happy 自己的 server。
  4. 核心保持 provider-neutral。Space、Actor、消息信封、事件是产品内一等概念；Tanka 只通过「身份源、渠道、数据曝光」三个可插拔接口进来。这与现有「核心不认识 Tanka」原则一致，也保住开源边界。

一、三家对照

先把三个参照物放在一起看。very-happy 要补的，正好是 Orca 缺的团队层和 Mirasim 缺的 Tanka 层。

值得借的

  • Orca：编排契约写给 agent 而不是写给人；Working / Needs You / Done / Idle 一个状态机投影到卡片、看板、feed、推送四处；自动化先禁用创建、手动跑通再启用。
  • Mirasim：Room 与 Session 分离，@助手在 Room 里开会话、结果回帖；会话互联有明确投递语义和熔断；「事项」把聊天、会话、待办串起来；面板的每个动作都有等价 CLI。

不照搬的

  • Orca 默认 yolo 权限、无 org；Mirasim 桌面优先、额度经济复杂、数据留自己云、共享会话一次只能一人驱动的体验要改良而非复制。

二、目标概念模型

新增或升级为一等对象的东西，以及它们的归属关系。单人用法不变：每个账号自带一个 personal Space。

四条取舍

  • Space 是共享边界，不是运行边界。运行仍发生在 Machine 上。
  • 信任分两档。共享的 Room、Task、Event、Team 是服务器可信明文（Teams 现状）；私有 Session 继续客户端加密。
  • 「发布到 Space」是投影。owner 的 daemon 解密后产出一份 Space 可见的副本，不把密钥交给别人。
  • 单驱动者。一个 Session 同时只有一个人或 Actor 能驱动，其余观看、评论、分叉或申请接管。
Space
共享边界。成员、角色、邀请；资源（会话、机器、Team、自动化）可授权给它。
Agent
从会话上的一个字段升格为命名、持久的对象：模型、默认机器与目录、skills/MCP、权限策略、owner。没有稳定身份就无法被 @、被授权、被审计。
Actor
统一可寻址身份：人类成员、命名 Agent、渠道 bot 都用同一种 @地址。
Room
人与 Actor 的对话面，和 Session（agent 工作记录）分离。不做把 bot 塞进群聊的模式。
Task
事项：负责人、协作人、状态、验收。从 Room 某条消息「记为事项」，从事项「开会话」，会话显示所属事项。
Event log
所有对象的状态变化统一进一条事件流，是「automate everything」的基础。

三、Agent 互通：结构化信封

在现有 team_message 和 session_message 之上定义信封 v1，不另起协议。

  • 谁发给谁：发送方 Actor（账号、Space、Agent、Session、代数）与接收地址（@agent、@session、@room，群发 @all / @idle）。
  • 意图枚举：status、question、handoff、result、heartbeat、escalation。
  • 授权上下文：发送方在目标 Space 的角色、本次允许的动作范围。
  • 安全规则：信封不能批准任何事、不能改配置、内含命令不执行；跨权限等级默认暂挂进决策队列。沿用已有的 T-39 规则。
  • 投递语义：目标空闲就开新一轮，运行中就作引导输入，离线就缓存并超时退回。回执分「已入队、已被模型读取、已回复」三档。
  • 熔断：每会话限流、链深上限、乒乓检测、账本保留，全部作为 Space 策略可配。
  • 暴露方式：官方 skill + MCP 工具（list_actors、read_session、send、start_session、ask、gate），与 Teams 现有 team_* 合并成一套。

跨账号路由：RPC 房间从按账号改成按 Space；跨机器派发复用已有的白名单 RPC；Team 成员允许是其他账号的 Agent，任务可跨账号认领与验收。

四、Automate everything

  • 事件是一等对象。会话状态、事项流转、Room 消息与 @、决策产生与消解、自动化运行、成员与机器变更、入站渠道事件，统一进 Event log。
  • 触发器从 cron 扩到事件。「当某事件满足条件时」，加 precheck、去重键、sticky key。公网入站 webhook 仍不做，入站统一经渠道进来。
  • 两种观测视图并存。feed 时间线用于离开后追赶；看板用于看现在谁卡住。
  • 面板即 CLI。UI 的每个动作都有等价命令，含脚本化批准和配置树 dry-run，让自动化和 agent 都能驱动面板本身。
  • 自动化属于 Space。成员可查看、复制、禁用；先禁用创建、手动跑通再启用。

五、Tanka 接入：三个可插拔接口

推荐路径：Authentik OIDC 作身份源（内含 Tanka 登录源，带组织树）；注册 Ridge provider 做只读曝光，同一曝光自动进 Tanka AI 与 MCP；事件经 Ridge 通知接口或 apodex-bot 推进 Tanka 群。三者都是已上线、有 owner 的面。

接口落地得到什么现状与依赖
身份源新增 OIDC 身份；email 为映射键Tanka 用户对应账号；部门与团队成为 Space 成员和角色的建议值账号已支持多登录身份；个人开源产品接公司身份源需公司侧确认
渠道把仓库外的 Tanka 适配器产品化：入站发送人按 email 映射成 Space 成员，群与 Room 绑定，出站可靠投递，引用回复回流在 Tanka 群里 @agent、收结果、回复决策事件订阅只有 app_mention；bot 不能私聊；出站失败不重试是已知欠账
数据曝光Ridge provider：只读查询空间、Room 摘要、会话摘要、事项、决策队列；按 JWT 主体做访问控制Tanka AI 和同事的 agent 能查 very-happy 数据，有审计需 Ridge 管理员激活；Ridge 的事件推送与统一凭证未上线，先只读

做不到、也不做的：把 Tanka 群当 Space 的存储或消息总线（建群拉人受限、无普通消息事件）；在 open.tanka.ai 注册自定义 agent（无此能力）；workmemory 以外的记忆写入（API 未披露）。

以后再接：Ridge 事件推送与统一凭证上线后，把 Event log 接进 Ridge；可选用 Ridge 组织树自动开出公司 Space。

六、分阶段清单

顺序原则：先把单人路径不变的地基打好，再做协作，再做自动化与 Tanka 产品化。

P0 地基 单人路径零改动

  1. Space、Member、角色、邀请；personal Space 默认存在。
  2. 资源归属加 Space 维度：会话、机器、Team、自动化可授权给 Space。
  3. Agent 一等化；Actor 统一地址。
  4. 决策队列按人跨 Space 聚合：permission、question、acceptance、gate。
  5. 通用 OIDC 身份源，Authentik 作为公司部署配置。
  6. 信任模型定稿：共享明文投影与私有加密的边界，「发布到 Space」的语义。

P1 协作

  1. Room、话题、DM；@Agent 开会话并回帖；来源芯片（如 tanka:群名）。
  2. 会话发布与单驱动者：观看、评论、分叉、接管申请。
  3. 信封 v1、投递语义、熔断；skill 与 MCP 工具合并。
  4. 跨账号路由与跨机器派发；Team 成员可跨账号。
  5. 机器出借：目录、agent、驱动者白名单。
  6. Task 事项作为 Room、Session、决策的枢纽。

P2 Automate everything

  1. Event log 一等化；事件触发器；自动化归属 Space。
  2. feed 时间线与看板并存。
  3. 面板即 CLI，含脚本化批准与配置 dry-run。
  4. Tanka 渠道产品化：身份映射、群绑定、可靠出站、回流。
  5. Ridge provider 只读曝光与 MCP。

P3 延伸

  1. 目标持续推进与任务图（对应 Mirasim 的 /goal、Orca 的 Run）。
  2. Ridge 事件流接入；公司 Space 自动开出。
  3. 在 Space 前提下重新评估上一轮 UX review 的拒绝项（bot 群聊、多租户触发服务）。

七、需要你拍板的五件事

  1. 共享内容走服务器可信明文（Teams 现状）是否可接受为产品承诺。私有会话「发布到 Space」用持续流还是一次性快照。
  2. 开源核心只做通用 OIDC，Authentik 和 Tanka 作为部署配置。公司侧接入是否需要先与负责人确认。
  3. Tanka 三个接口放仓库内的可插拔 provider，还是独立 adapter 仓库。
  4. P0 是否先只做前四项（Space、归属、Agent、决策队列），OIDC 与信任模型并入 P1。
  5. 公司 Space 从 Ridge 组织树自动开出，还是手工建。

回答第 1 和第 4 条，就能把 P0 细化成可开工的 spec。
