# 完备性 critic：保留集（8 kept + 5 contested）对照全稿与取证底图

**结论**：按当前 tally，清单答不出 Owner 简报里的三件事——① 未来方向（幕僚长 / 角色 bot / harness）**零桥接**；② 「跑完≠完成」的验收哲学零支持；③ 手机/PWA 只剩半条。另外保留集自身有 5 处依赖断裂，其中 2 处会让保留项**不可实现或制造新的信任缺口**。

## A. 保留集内部断裂（先修这里，否则逐条评审会卡住）

- **T-34 保留、T-35/T-36 全丢 = 拆掉唯一编排面而无承接**。T-34 原文就写「编排能力以工具面形式回到普通会话（见 T-35）」；T-35 一丢，它只剩「删页面」。Owner 明说未来要做 bot/幕僚长/角色 bot，取证底图 `workflow-layer §5` 的五个缺口（账号级读取面、事件订阅、outcome、出口、角色模型）**只有 outcome（T-09）被保留**。至少保留一个最小桥：`spawnedBy → reportTo` 泛化 + 队列条目的 `author` 字段（T-36 自己标注的「今天先落地的最小部分」）。否则 T-34 应改写为「语音降级为输入法 + bot 会话不再隐藏」。
- **T-03 保留「本会话始终允许」、T-27 丢 = 隐形常设授权**。`product-map §6.13`：今天已经没有查看/撤销入口；vh 有 5 次「UI 说的 ≠ 机器实际的」记录（C1–C10）。不可见的授权=不可撤销的授权。最低限度：把「已允许 n 项（查看/撤销）」塞进 T-03 本身，否则删掉该按钮。
- **T-01 丢，但 T-02/T-04/T-06 都建立在它之上**。T-04 要落账的「attention 记录」没有定义者，三套并行分类（侧栏 Status / 看板 Waiting / 铃面板，`product-map §6.1`）继续存在。建议把「唯一分类器 = `boardItems.lifecycleOf`」并进 T-02 的实现条款，而不是当独立项砍掉。
- **T-22 保留、T-21 只是 contested**：PR/CI 要挂在分支上。若 T-21 被裁掉，T-22 必须自带分支来源（daemon 按 cwd 读当前分支），否则不可实现。
- **T-11/T-12 保留、T-25 丢 = 评审面没有触发器**。除 yolo 与逐工具审批外，没有任何机制让 agent 停下来等人看 diff。建议把「每轮停下等我看」降格为会话级开关写进 T-11（Paseo `Auto Review` 先例），不新增出站枚举（铁律 14）。

- **T-13 白屏兜底**：唯一会让 Owner **丢失未发送输入**的故障（`pains F1`、B-027/B-003、铁律 17 已写明成因）。队列与状态词汇全部建立在「屏幕上写的是真的」之上。
