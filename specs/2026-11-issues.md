## 设计

### 1. 概念

| 名词（中 / 英） | 定义 |
|---|---|
| **Issue** | 账号内的持久工作项，编号 `VH-N`。人建，人关闭。 |
| **执行 / Run** | issue 的一次执行 = 一个会话。一单多次：指派、@、重试、换 agent 各起一次。 |
| **派发 / Dispatch** | server 给某台机器 daemon 的工作单：`spawn`（起会话）或 `message`（往活会话投一条评论）。 |
| **时间线** | 评论 + 系统条目（状态、指派、执行）同一列表。 |

```text
Account
 └─ Issue (VH-N, status, assignee, project?, parent?)
     ├─ IssueComment × N  （人 / agent / system；@agent 结构化）
     ├─ IssueRun × N      （1 run = 1 session；trigger; status）
     │    └─ IssueDispatch × N （spawn 一次 + message 若干；daemon 认领）
     └─ links（第二期 PR，本期空）
IssueSequence(accountId) → 下一个 N
执行仍在 Machine ─ daemon ─ wrapper；会话加入 issue 的项目（via='issue'）
```

**`IssueSequence`**：`accountId @id`、`last Int`。新建 issue 在同一事务里先用一条原子语句取号：`INSERT … ON CONFLICT ("accountId") DO UPDATE SET last = last + 1 RETURNING last`。不用 `Account` 上的列：`Account.seq` 是每条 update 都写的热点行，SERIALIZABLE 下会互相冲突重试。

- **建单事务用 READ COMMITTED（B-872c，QA42 P2-1）**。在 SERIALIZABLE 下，同账号并发建单对同一行做更新，后提交的会报 40001。真实 PG 实测 8 路并发约一半返回 409，pglite 测不出来。改为 READ COMMITTED 后，取号语句持有的行锁会让同账号的建单排队执行，配额计数等后续读取都在锁后进行；事务回滚时号码一起回滚，编号不留空洞。同一 `requestId` 并发提交时，后到的请求在 `requestKey` 唯一索引上失败（P2002），服务端重试后返回先到者建的单。其余写入仍用 SERIALIZABLE。Todos 导入也走同一个取号函数。
- **服务端重试**：所有 issue 写入在 40001、40P01（P2034 / P2010）时自动重试 8 次，退避为 `50·n ms` 加 0–100 ms 抖动，P2002 另外重试 3 次。全部用完才返回 409 `transaction_conflict`。
- **门禁**：`scripts/ci/issues-concurrency-smoke.mjs` 在 server container smoke 的真实 PG16 上，对同一账号做 3 轮、每轮 16 路并发建单，要求全部 200、编号连续，客户端不做重试。修复前用同一个脚本，16 路里有 10 路返回 409。

#### 2.6 加密口径：服务端明文（推荐，需 Lead 确认）

title、description、评论、run 元数据全部服务端明文，Web 标注「Issue 内容对服务器可见」（与项目页同一文案位）。理由：

1. **同档一致**：Projects（Q4 拍板明文）、Teams、AttentionItem（D1 明文）、被并入的 Todos（KV base64 明文）全是这一档；Issue 吸收 Todos，若改成加密，迁移就必须在有密钥的客户端完成，server 懒导入不可行。
2. **server 必须读正文**：初始 prompt 由 server 拼（§3）；评论路由、`/note` 判定、`@` 结构、⌘K 服务端搜索（`?q=` ILIKE）、`issue_get` 都要明文。客户端加密就得把这些全挪到 daemon/Web，并且无机器在线时无法开跑、无法搜。
3. **MCP 读取**：agent 经 wrapper 用账号 token 读；加密要求 wrapper 拿账号内容密钥，扩大密钥面。

风险：服务端运维可见。缓解：日志 / metrics / Sentry 不记 title、description、评论正文（server 线写源码断言，与 B-867 同法）。

### 3. 指派即开跑

#### 3.1 触发点（server，同一事务）

| 事件 | 动作 |
|---|---|
| 新建 issue，assignee=agent 且 status ∈ runnable（todo/in_progress/in_review/blocked；未给 status 时默认 todo） | 建 run（trigger `assign`）+ spawn 派发 |
| assignee 改为另一个 agent 配置，且 status runnable | 新 run（`assign`）；旧活 run → `superseded` |
| status 从 backlog/done/cancelled 改到 runnable，assignee=agent 且无活 run | 新 run（`assign`） |
| status 改到 backlog | 只记归属；活 run 不动（人想停就点「停止」） |
| 人点「重试」/「换 agent 重跑」 | `POST /v1/issues/:id/runs` 新 run（`retry`），旧活 run → `superseded`；`reassign:true` 时同时改 assignee |
| 人评论 | §6 路由 |

assignee=self / none / 改成 backlog：不开跑。

#### 3.2 派发与认领（复用 Teams operation 模式，不新增 server→daemon RPC）

```text
server: IssueRun(queued) + IssueDispatch(spawn, queued)
daemon issue worker (每 5 s): GET /v1/issues/dispatch?machineId&workerVersion=1
  → POST /dispatch/:id/claim {machineId} → claimId；run → claimed
  → 校验账号（B-850d resolveAccount，拒跑不回落本机登录）与目录
  → spawn-happy-session {directory, agent, model, permissionMode, agentProfileId,
       spawnedBy:'issue', environmentVariables:{VH_ISSUE_ID, VH_ISSUE_RUN_ID}}
  → joinProject(sessionId, projectId, via:'issue')（有项目时）
  → sendUserMessage(prompt, {localId:`issue-<dispatchId>`, sentFrom:'issue', model, modelIntent})
  → POST /dispatch/:id/complete {claimId, sessionId}；run → running，startedAt
  失败 → /fail {error}；run → failed（§3.7）
```

- **spawn 失败语义（B-874c，QA43 P2-1）**：明确失败（目录建不出来、env/agent/账号校验在起进程前就拒、wrapper 已退出）立即 `/fail {error}`，run failed 并进「需要我决策」（无会话的失败由 Web 按 `failureAckedAt` 合并显示）。结果不明（webhook 超时且进程未确认停掉等）时 daemon **不发** `unknown:true`：保留认领，每次轮询按 `metadata.issue.runId` 找会话，找到就照常 complete；`ISSUE_SPAWN_UNKNOWN_GRACE_MS`（60 s，小于 120 s 租约）后仍找不到就 `/fail`（reason 写明原因）。daemon 中途死掉时由租约兜底（3 次过期 → run failed）。server 的 `unknown` 参数保留兼容，不再由新 daemon 使用。

- 目录解析：`assignee.directory` > issue 项目在该机器上的目录（primary 优先）> 400 `issue_no_directory`（建单/指派时就拒，不进队列）。
- 认领租约 120 s：claimed 超时未 complete 的派发退回 queued（attempts+1，≥3 次 → run failed）。
- **prompt 在 claim 时冻结（B-872c，QA42 P2-3）**：每次 claim 都按当时的 issue 和评论重新拼 prompt，写进 dispatch payload。daemon 只认 claim 返回的那份。claim 之后再改标题或加评论，不会改动已冻结的 prompt。在 claim 和 complete 之间路由给这个 run 的评论，会在 complete 时作为 message 派发补发。lease 过期退回 queued 时，会清掉上次冻结的 prompt，下次 claim 重新拼。poll 返回的 `spawn.prompt` 只是**预览**：对 queued 的派发，它在 poll 时现拼，内容和紧接着的 claim 一致，但不保证这就是 run 最终收到的 prompt。
- 首条消息的 `issue-` localId 前缀加进 `isOwnerAuthoredMessage` 的排除表（server 线），否则 issue 派发会被当成 Owner 回复去清自动化 attention。
- 机器离线：派发一直 queued；Web run 行显示「等待 mac-office 上线」。

#### 3.3 注入内容

首条消息 = `buildIssueInitialPrompt`（wire 纯函数，server 生成存进 dispatch payload）：标题、状态/优先级/labels/due、描述、最近 10 条人/agent 评论、触发评论（@ 启动时）、状态规则段（§5）。**项目上下文不重复拼**：会话以 `via:'issue'` 入项目后，B-645 injector 在这条消息发出前自动加 P 前缀（实测路径同 automation）。

#### 3.4 run 启动时的状态（推荐）

run 进入 running 时 server 把 `todo → in_progress`（`issueStatusOnRunStart`，actor=system，`statusRunId=run`）。agent 规则里仍要求自己设 in_progress（幂等）。理由：看板立刻反映「在做」，并为 §3.7 的失败回退提供确定的锚点；只有 todo 会被动，in_review/blocked 上再次触发不改。

#### 3.5 同一 issue 已有会话在跑时（推荐：同 agent 并入，否则新开）

`chooseIssueDelivery`（wire 纯函数）：

| 情况 | 动作 |
|---|---|
| 目标 agent（同机器）有活 run 且会话 live | 并入：`message` 派发，作为**排队**消息投递（不 steer、不打断） |
| 活 run 还在 queued/claimed（会话未起） | 吸收：不派发，初始 prompt 构建时会读到这条评论 |
| 无活 run / 会话已死 / @ 的是另一个 agent | 新 run（`comment` 或 `mention`） |
| 人点重试 / 换 agent | 总是新 run，旧活 run superseded |

理由：同一个 agent 的上下文最值钱，排队不打断与 Multica「join the pending run」一致；不同 agent 并行各起各的。

#### 3.6 superseded 与旧会话

旧会话保留不杀（人可继续看、手动聊）。它的 `issue_update / issue_comment` 返回 409 `issue_run_not_current` 和一句「本 issue 已转给新的执行，请停止改动」。worktree：字段保留，本期 daemon 忽略（开放问题 Q6）。

#### 3.7 执行失败（推荐：按 Multica 回退，但只回退本 run 造成的 in_progress）

失败 = spawn 失败、账号拒跑、认领 3 次超时、wrapper crash（daemon 报 `crashed`）。处理：

1. run → failed，记 error，时间线写一条 `run` 系统条目。
2. issue 若仍是 `in_progress` 且 `statusRunId == 本 run` → 回 `todo`（`issueStatusAfterRunFailure`）；agent 已改成 in_review/blocked 或人改过的不动。
3. 进「需要我决策」（§7），动作「重试 / 换 agent / 知道了」。
4. 不自动重试（第二期只重试瞬时故障，最多 2 次）。

正常结束（会话 exited / 被归档）→ run ended，不改 issue 状态。会话 idle → run idle，不改状态、不发提醒（agent 没按规则交付时，靠人看到「agent 空闲 · 仍在进行中」标记，Q7）。

### 6. 评论线程

路由 `routeIssueComment`（wire 纯函数）+ 投递 `chooseIssueDelivery`：

| 评论 | 路由 |
|---|---|
| agent 写的 | 不唤醒任何人（防回环；agent 之间 @ 第三期） |
| 人写、`/note` 开头 | 只存、只显示，不触发 |
| 人写、带 @agent（结构化 `mentions[]`，≤3 个） | 每个被 @ 的 agent：有活会话 → 投递；没有 → 新 run（`mention`）。**任何状态都触发**（显式意图，包括 done；但 agent 改不了已关闭 issue 的状态，只能评论） |
| 人写、无 @ | assignee=agent 且 status runnable → 交给它（有活会话投递，没有新 run `comment`）；backlog / done / cancelled / 非 agent assignee → 不触发 |

- `@` 不从正文解析：Web 输入框 `@` 弹出可选 agent（Claude / Codex / pi，机器默认取 assignee 的机器，否则项目主目录机器），提交结构化 mentions；CLI `--mention codex[@machine]`。正文里的 `@codex` 只是文字。
- @ 未在 assignee 的 agent：新 run 的配置 = 被 @ 的 agent + 指定机器（缺省 assignee 机器）+ 该 agent 在项目上的默认账号/模型（`resolveLaunchAgentProfile`）；**不改 assignee**。
- agent 评论显示为 agent 身份：`Codex · mac-office · 第 2 次执行`，点开跳会话。
- 投递到活会话的消息：`issue-<dispatchId>` localId、`sentFrom:'issue'`、`delivery` 省略（=排队到下一轮）。
- 人评论处理掉 @我：同一 issue 上人发任何评论 → 该 issue 所有 `ownerAckedAt` 为空的 owner 提及置为已处理（并消 §7 条目）。

### 7. 接入「需要我决策」

三类会话相关事件走现有 `AttentionItem`（server 内部写，`source:'issue'`，`links:[{type:'issue', ref:issueId, label:'VH-12'}]`，sessionId = 该 run 的会话）；没有会话的执行失败走 Web 合并（与自动化 run 同一模式）。

| 事件 | 条目 | key | 消项 |
|---|---|---|---|
| agent 改 in_review | `kind:'decision'`，标题「VH-12 待验收 · <标题>」，body=交付评论，选项 `done`「完成」/ `return`「退回」 | `issue-review:<issueId>` | 看板点「完成」→ issue done；点「退回」→ issue todo，Owner 附言写成人评论（按 §6 自动投回 agent）；issue 因任何原因离开 in_review → resolved（`resolvedBy:'issue-status'`） |
| agent 改 blocked | `kind:'blocked'`，标题「VH-12 卡住 · <标题>」，body=缺什么 | `issue-blocked:<issueId>` | 离开 blocked → resolved；人在 issue 上评论**不**自动消（与 B-766 S-1d 一致：普通回复不等于处理了决定） |
| 执行失败（有会话：wrapper crash） | `kind:'blocked'`，「VH-12 执行失败」，links 加 panel | `issue-run-failed:<runId>` | 新 run 启动、人 ack、issue 关闭 → resolved/dismissed |
| 执行失败（无会话：spawn/账号/认领失败） | 不写 AttentionItem；`IssueRun.status=failed && failureAckedAt=null` 由 Web `needsYou.ts` 合并（同自动化 run） | — | `POST /runs/:id/ack-failure`、重试、issue 关闭 |
| agent @我 | `kind:'todo'`，「VH-12 @你 · <评论首行>」 | `issue-mention:<commentId>` | 人在该 issue 上评论、或在看板点「知道了」、或 issue 关闭 |

- issue 被人改成 done / cancelled / 删除：该 issue 所有开放条目 dismissed。
- push 沿用 AttentionItem 规则（decision/blocked/todo 推一次）。
- 条目 key 带 issueId，同一 issue 反复进 in_review 只会重开同一条（`repostCount+1`），不刷屏。
- wire 只加枚举值：`ATTENTION_SOURCES += 'issue'`、`ATTENTION_LINK_TYPES += 'issue'`、`ATTENTION_RESOLVED_BY += 'issue-status'`。响应侧这三个本就是开放字符串，旧 Web 照常显示（只是没有 issue 链接按钮）。

**REST（全部在该账号开启 Issues 后——`VH_ISSUES_ENABLED=true` 或账号在 `VH_ISSUES_ACCOUNTS`；其他情况都是关，404 `issues_disabled`）**

| `POST /v1/issues/agent/update`、`/agent/comment` | agent 写（`sessionId` wrapper 盖） | wrapper |
| `GET /v1/issues/dispatch`、`POST …/dispatch/:id/claim|complete|fail` | 派发认领 | daemon |
| `POST /v1/issues/runs/:runId/session-event` | running / idle / exited / crashed | daemon |

**todo id 别名（B-874d）**：`POST /v1/issues` 可带 `legacyTodoId`（调用方的 todo id，CLI 填 `todo add --id` 的 U），写入 Todos 导入用的同一列，账号内唯一（`@unique([accountId, legacyTodoId])`）。规则：
- **查找**：所有接受 `:id` 的路由（`loadIssue`）先按 `{accountId, id}` 精确查，查不到才按 `{accountId, legacyTodoId}` 回退，两步都限定当前账号，B 账号拿 A 的 U 只会得到 404。issue id 是服务端 `randomUUID()`，todo id 是客户端 UUID，两者格式相同，撞上的概率可以忽略（v4 随机 122 位）；即使撞上，也是 issue 自己的 id 优先，不会被别名覆盖。
- **幂等**：先按 `requestId` 查，再按 `legacyTodoId` 查；同一个 U 已有 issue 时返回那条，换了 `requestId` 也一样，绝不新建第二条。内容是否一致由 CLI 比对（与 KV 相同：内容不同报冲突）。
- **已删除**：U 对应的 issue 已软删时，返回 `404 issue_todo_deleted`，不复活、不新建。这与 KV 一致：KV 删除留下 tombstone，`get` 读到 null，同一 id 不能再用。`GET /v1/issues/U` 仍返回墓碑（`deletedAt` 有值），CLI 把它显示为 `null`。
- **兼容**：旧 server 的 zod 会剥掉未知字段，新 CLI 在旧 server 上退化为 B-874 的行为（输出 issue id，用 U 查不到）。所以先发 server，再发 CLI。

**错误重试约定（B-872c）**：`409 transaction_conflict` 表示服务端重试已经用完，**可以重试**。Web 和 CLI（命令、MCP 工具、daemon worker）收到它时都要**自动重试**：用同一个 `requestId` 和同样的参数，退避约 200 ms·2ⁿ 加抖动，最多 5 次，之后才把错误显示给用户。建单、评论、run、agent 写入都带 `requestId`，所以重试是幂等的。PATCH 带 `ifVersion`，重试不会覆盖别人的修改；派发的 claim、complete、fail 本身就是幂等或条件更新。其余 409（如 `issue_version_conflict`、`issue_dispatch_claim_mismatch`、`attention_item_stale`）表示业务冲突，**不能**自动重试。

**Socket（账号级 update，`user-scoped-only`，全量快照，按 version 取大）**：`{t:'issue', issue}`、`{t:'issue-comment', comment}`、`{t:'issue-run', run}`。不做 seq 补洞：Web 断线重连 / `resumeSync` 时用 `updatedSince=<上次 asOf>` 拉增量（Issues 列表 + 当前打开详情）。不新增轮询；没有 socket 时（旧 server）不显示 Issues。

- **详情 `/issues/:key`**：标题 / 描述（Markdown，显式保存，`ifVersion` 冲突提示）；右栏字段（状态、优先级、assignee 选择器——复用新建会话的机器 + agent + 账号 + 模型选择器、项目、labels、due、父 issue）；时间线（评论 + 系统条目；评论框支持 `@` 选 agent 和 `/note`）；执行记录列表（第 N 次、trigger、agent·机器、状态、时长，点开跳会话；失败行「重试 / 换 agent」）；状态改成 done 的按钮只给人（本来就只有人在 Web 上）。
- **项目页**：「Issues」区（该项目未关闭 issue，按状态分组，快速新建）。
- **⌘K**：issue 分组（本地已加载 issue 按 key/标题匹配，`VH-12` 直达）；无匹配时追加「新建 issue：<查询>」（与「新建对话」并列）。
- **会话头**：绑定 issue 的会话显示 `VH-12` 芯片（读 run 表，不依赖 metadata），点回 issue。
- **需要我决策**：`needsYou.ts` 加第三路（失败且未 ack 的 run）；AttentionItem 的 `links[type=issue]` 渲染成「打开 VH-12」。
- **数据层**：`sync/issuesStore.ts`（zustand，与 `storage.ts`/`sync.ts` 热区分离；`sync.ts` 只加三行 update 分发）。
- 设计：沿用紧凑工作台；颜色只用 tokens；`--accent` 只给「运行中」；390 coarse / 桌面 × 明暗验收。

### 11. CLI 范围（N1 或 K2）

- **daemon issue worker**（`daemon/issues/worker.ts`）：5 s 轮询（与 Teams worker 同节奏，独立 tick）、认领、spawn（账号拒跑走 B-850d `resolveAccount`）、`joinProject(via:'issue')`、`sendUserMessage`、complete/fail；本地 journal 防重复（同 Teams receipts）；`message` 派发：会话 live → 发送；不 live → fail（server 改为新 run）。
- **会话事件**：wrapper 起停 / 回合结束 / crash → `session-event`（复用 daemon 已有的会话生命周期钩子；基础设施退出 SIGTERM 只报 `exited`，与 B-505 一致不算失败）。
- **MCP**：`issue_get / issue_update / issue_comment / issue_list`（`happy-cli/src/issues/tools.ts`），入参用 wire schema 校验。
- **注入**：injector 增加 issue digest（§5）；首条和评论消息由 server 拼好，daemon 原样发送。
- **metadata**：spawn env `VH_ISSUE_ID / VH_ISSUE_RUN_ID` → `metadata.issue`；能力位 `issue-v1`。
- **`very-happy issue`**：`list [--status] [--project] [--mine] [--json]`、`show <VH-N>`、`create --title [--desc] [--assign codex@machine] [--project] [--priority] [--label]…`、`update <VH-N> [--status] [--assign] …`、`comment <VH-N> <text> [--mention codex]`；在 `HAPPY_SESSION_ID` 存在的会话里运行时一律走 agent 路由（同样不能设 done）。
- **`very-happy todo`** 别名层与 skill 文本（§8）。
- CLI 测试按 BRIEF 用 `flock`；worker 用隔离 `HAPPY_HOME_DIR` 实测。

### 12. Server 范围（S）

迁移与表（§2）；开关 `VH_ISSUES_ENABLED`（仅 `true` 开，每请求读 env）；`sources/app/issues/`：`rules.ts`（引 wire 纯函数）、`store.ts`（inTx + afterTx emit）、`dispatch.ts`、`attentionBridge.ts`（§7，调 attention store 内部 API）、`todoImport.ts`；路由 `issueRoutes.ts`；`isOwnerAuthoredMessage` 加 `issue-` 前缀；会话归档钩子 → run ended；`VH_ISSUES_ENABLED` 开关；日志不记正文（源码断言 + 全流程日志捕获集成测试，搜不到 title/description/评论标记串）；必须有走真实路由的测试（Fastify inject / pglite），包括「agent 设 done 被拒」「并发建单编号不重复」「重复 claim 只有一个成功」「导入重跑幂等」。

### 13. 三条线的接口边界

| 接口 | 生产方 | 消费方 | 定义 |
|---|---|---|---|
| REST 人类路由 + update 事件 | S | W、C（CLI 命令） | §9 + wire views |
| agent 路由 + `IssueSessionContext` | S | C（MCP / injector） | wire `IssueAgent*Schema` |
| 派发队列 + session-event | S | C（daemon worker） | wire `IssueDispatch*` |
| 首条 / 评论 prompt 文本 | wire 纯函数（S 调用） | C 原样发送 | `buildIssue*Prompt` |
| 路由 / 状态规则 | wire 纯函数 | S 强制，W/C 预检与置灰 | `routeIssueComment`、`checkAgentStatusChange` 等 |
| AttentionItem 条目 | S | W（现有汇报板 UI） | §7 |

并行方式：wire 先合（本 PR）；S、W、C 同时开工，W 用 fixture/mock server 先做 UI，C 用本地 standalone server 联调；三线各自 PR，S 先合。

回滚：

| 层 | 动作 | 影响 |
|---|---|---|
| 开关 | 删掉 `VH_ISSUES_ENABLED`（或设非 `true`）+ `rollout=switch` | Web 退回旧 Todos（读 KV，看不到 Issues 内改动）；派发停发；表保留。**残留的 issue 决策项（QA42 P2-2）**：开着开关时生成的条目（`issue-review:` 待验收、`issue-blocked:` 等）在关闭开关后仍会留在「需要我决策」里。待验收条目点「完成」或「退回」会返回 409 `attention_item_stale`，原因是 `settleIssueReview` 在开关关闭时直接拒绝，不改 issue。处理方法：对该条目执行 `resolve`（「知道了」，实测 200 / dismissed），或者归档对应会话（实测条目变为 `dismissed / session-archived`）。回滚到旧镜像后不会出现这个问题，旧代码把它当普通条目处理，见下一行 |

## 验收标准

- [ ] **E2E 主路径**（真实 server + 隔离 daemon + 真实 Codex，浏览器操作）：新建 issue → 指派 Codex（某机器）→ 5 s 内 run running、issue 自动 in_progress → agent 调 `issue_update in_progress`、改代码、`issue_comment`、`issue_update in_review` 带总结 → 「需要我决策」出现「VH-N 待验收」并推送一次 → 点「完成」→ issue done、条目 resolved、时间线完整、run 可跳会话。
- [ ] agent 设 done / cancelled 被 server 拒（MCP 与 CLI 两路）；in_review / blocked 无评论被拒；已关闭 issue agent 改不了。
- [ ] backlog 指派不开跑；改到 todo 才开跑；换 agent 新 run、旧 run superseded 且旧会话写入被拒。
- [ ] 评论：无 @ 投给活会话（排队，不打断）、无活会话新开；@另一个 agent 新 run 不改 assignee；`/note` 不触发；agent 评论不触发；@我 进决策列表，人评论后消项。
- [ ] 失败：账号拒跑 / spawn 失败 → run failed、in_progress 回 todo、进决策列表（Web 合并路），重试后消项；wrapper crash 走 AttentionItem 路。
- [ ] 退回：看板点「退回」带附言 → issue todo、附言成人评论并投回 agent。
- [ ] Todos 迁移：导入后条数一致、open/done 映射正确；重跑 0 新增；旧 CLI 写 KV 后再导入只补差；冲突写系统评论；KV 未删。`very-happy todo list/add/complete/reopen/delete` 在新 server 上对 Issues 生效且输出格式不变。
- [ ] 兼容：旧 Web 连新 server 不报错；旧 daemon 机器在选择器中标「CLI 过旧」；开关关闭等同旧 server。
- [ ] 并发：并发建单编号连续不重复；同派发并发 claim 只一个成功；P2034/40001 重试有测试。
- [ ] Web：list / board / 筛选 / My Issues / 详情 / 项目区 / ⌘K / 侧栏，1280 与 390 coarse × 明暗，无横向溢出，触控 ≥44px；中英文案；README / docs / 站内文档 / changelog 同步。

## 风险

1. **派发延迟**：5 s 轮询 → 指派到开跑最长约 5 s + spawn 时间。可接受；第二期可加 machine-scoped ephemeral 唤醒。
2. **issue 派发被当 Owner 消息**：必须在同一个 server 发布里改 `isOwnerAuthoredMessage`，否则自动化 attention 被误清；server 线验收项。
3. **评论刷屏 / 回环**：agent 评论不唤醒；每 run 每小时 30 条上限；同 key 条目只重开不新增。
4. **迁移双写窗口**：过渡期旧端写 KV、新端写 Issues，靠重跑导入补齐；两边都改按 issue 为准并留系统评论，不静默丢。
5. **明文**：见 §2.6，日志不记正文。
6. **指派目录错**：目录解析失败在建单时就拒，不让 run 进队列后才失败。
